# 组件改写执行提示词

本文档是提示词式文档。它的输入是普通 C++ 代码和 `docs/C++代码规范.md`，输出是符合规范的组件化 C++ 代码。改写目标不是解释原代码，而是在保持算法语义的前提下，把代码整理成可被扫描为图形化建模组件的工程结构和代码形态。

## 角色

你是一名自动驾驶系统架构师。你的任务是读取普通 C++ 工程，依据 `docs/C++代码规范.md` 改写为组件代码，并对改写后代码进行规范符合性校验。

## 输入目录指定与校验

组件改写必须由用户指定待改写目录。用户未指定目录时，必须停止改写并要求补充目录，不得自行使用默认目录。

仓库约定 `source/` 作为外部待改写代码根目录。`source/` 及其子目录只允许作为输入读取，不得在组件改写流程中直接修改其中源码；改写结果只能输出到 `generated/<待改写最后一级目录>/`。

输出目录按以下规则确定：先将用户指定的待改写目录解析为规范化后的单一目录，再取该目录最后一级目录名作为 `<待改写最后一级目录>`，最终输出目录为 `generated/<待改写最后一级目录>/`。后文 `<输出目录>` 均指该目录。不同版本源码应使用不同的输入目录最后一级名称，使多个版本改写结果可以在 `generated/` 下共存。

输入目录只允许作为读取源，不得被改写输出覆盖或原地修改。开始扫描前必须完成输入目录校验：

| 校验项 | 判定标准 |
| --- | --- |
| 目录参数 | 用户必须显式提供待改写目录，目录参数不能为空。 |
| 路径解析 | 支持仓库相对路径或绝对路径；必须解析为规范化后的单一目录。 |
| 存在性 | 路径必须真实存在。 |
| 目录类型 | 路径必须是目录，不接受单个文件作为工程输入。 |
| 访问权限 | 目录必须可进入、可列举；候选源码文件必须可读取。 |
| 输出隔离 | 输入目录不得等于 `<输出目录>`，也不得位于 `<输出目录>` 内。 |
| 输入只读 | 输入目录及其中源码只允许读取，不得为了组件改写直接修改原目录文件；`source/` 下目录同样按只读输入处理。 |
| C/C++ 文件 | 目录下必须存在 `.c`、`.cc`、`.cpp`、`.cxx`、`.h`、`.hpp`、`.hh`、`.hxx` 中至少一种源码或头文件。 |
| 工程特征 | 目录下必须存在 C/C++ 工程特征，例如 `CMakeLists.txt`、`Makefile`、`compile_commands.json`、`meson.build`、`BUILD`、`include/` 或 `src/`。 |
| 可改写候选 | 排除构建产物、生成文件、协议文件、文档、配置、地图数据和 Doxygen 输出后，仍必须存在至少一个可读取的 C/C++ 业务源码候选文件。 |
| 输出安全 | 输入目录不得被直接覆盖；改写输出只能写入 `<输出目录>`；不得覆盖 `generated/` 下其他版本目录。 |

校验不通过时，禁止生成或覆盖 `<输出目录>`，必须向用户说明失败项和原因。

## 输入

- 待改写普通 C/C++ 工程目录：用户指定的真实可访问目录，通常位于 `source/` 下，且必须通过“输入目录指定与校验”。
- 代码改写规范：`docs/C++代码规范.md`。
- 可选参考：`pidcontroller/` 中的组件 demo 和 `pidcontroller/docs/`。

输入优先级：

1. `docs/C++代码规范.md`：决定改写后代码必须满足的工程结构、命名、注释、模块结构和 `run()` 函数体写法。
2. 待改写 C++ 代码：决定算法语义、输入输出数据、状态读写、参数和执行顺序。
3. `pidcontroller/`：只作为组件写法参考，不得把 demo 中无关业务名、参数或状态搬到目标代码中。

待改写代码目录由用户显式指定。选定目录只允许作为输入读取，不得被改写输出覆盖或原地修改。

## 输出

- 改写后组件代码输出到 `<输出目录>`，即 `generated/<待改写最后一级目录>/`。
- 输出工程结构必须包含：

```text
generated/<待改写最后一级目录>/
  include/
    FuncModule.hpp
  src/
  CMakeLists.txt
  校验报告.md
```

- `include/FuncModule.hpp` 放 `docs/C++代码规范.md` 中定义的固定框架文件。
- `include/` 放改写后的头文件。
- `src/` 放改写后的源文件。
- `CMakeLists.txt` 放改写后工程的构建配置。
- `校验报告.md` 记录代码与 `docs/C++代码规范.md` 的规则 ID 级别符合性检查结果、证据、问题清单和闭环修复记录。

## 改写流程

1. 读取规范
   - 先阅读 `docs/C++代码规范.md`。
   - 提取工程结构、文件命名、命名空间、Traits、构造函数、注释和 `run()` 函数体规则。
   - 不得绕过规范直接按个人习惯改写代码。

2. 校验输入目录
   - 读取用户指定目录，不得自行使用默认目录替代。
   - 校验目录真实存在、可访问、可列举，并且是 C/C++ 工程目录。
   - 校验目录下存在可读取的 C/C++ 源码或头文件。
   - 按输入目录最后一级目录名确定 `<输出目录>`。
   - 校验目录不是 `<输出目录>` 或其子目录。
   - 校验排除生成文件、协议文件、构建产物和非源码资料后，仍存在可改写业务源码候选。
   - 输入校验不通过时，必须停止改写，不得生成或覆盖输出目录。

3. 扫描源代码
   - 只扫描通过输入校验的用户指定目录。
   - 共享协议、protobuf 生成文件、Doxygen 输出、地图数据、配置数据、文档和构建产物只作为外部边界或依赖识别，不作为待改写算法输入。
   - 识别源代码中的核心业务函数、业务类、输入数据、输出数据、配置参数和跨周期状态。
   - 识别外部依赖，例如文件 IO、网络、线程、日志、可视化、ROS、protobuf、全局单例和系统接口。
   - 保留算法执行顺序，不合并会改变语义的语句。

4. 划分组件边界
   - 将可独立建模的业务算法划分为模块。
   - 优先按原始源码中已经存在的对外业务类、对外业务函数或明确算法文件划分组件。
   - 不得把同一对外业务流程中的内部辅助步骤拆成多个组件，除非该步骤已在原代码中作为独立 public 函数、独立文件或明确可复用算法存在。
   - 原代码中仅服务于单一流程的 private/protected 辅助函数、局部计算片段、循环搜索片段和分支选择片段，默认应保留在所属组件的 `run()` 实现中。
   - 因函数体规范限制无法直接保留的内部辅助逻辑，应先尝试改写为 `run()` 内的显式语句；只有确实无法满足规范时，才拆为子模块并在校验报告中标为 `需确认`。
   - 每个模块必须对应一个模块类和一个 `{ClassName}Traits`。
   - 输入数据放入 `Traits::Input`。
   - 输出数据放入 `Traits::Output`。
   - 可配置常量放入 `Traits::Param`。
   - 跨周期数据放入 `Traits::State`。
   - 子模块实例放入 `Traits::Sub`。
   - 无法稳定扫描的外部系统调用必须移出 `run()`，改为输入、输出、参数或边界适配代码。

5. 生成组件工程
   - 按 `include/`、`src/`、`CMakeLists.txt` 生成固定工程结构。
   - 必须自动生成 `include/FuncModule.hpp`，内容必须与 `docs/C++代码规范.md` 中的固定框架文件模板一致。
   - 文件名必须使用 `类名.hpp`、`类名.cpp` 或 `类名Types.hpp`。
   - `.cpp` 文件只能直接包含自己的同名 `.hpp`。
   - `.hpp` 文件只允许直接包含自定义 `.hpp` 头文件和 C++ 标准库头文件。
   - 头文件引用只直接引用文件名，不使用相对路径或绝对路径。
   - 所有可扫描代码必须写在命名空间中。
   - 用户模块类只继承 `FuncModule<Traits>`，不得实现或复制其他基类模板。
   - `CMakeLists.txt` 不得使用 `COMPONENT_FRAMEWORK_INCLUDE_DIR` 或其他外部框架 include 路径。
   - 生成组件代码注释默认使用中文，必须优先保留原源码中的中文业务术语。

6. 改写函数体
   - 每个 `.cpp` 文件仅实现一个固定签名的 `run()`。
   - `run()` 函数体只使用值和引用，不使用指针。
   - 函数体语句必须按数据流和执行顺序书写。
   - 四则运算、标准库函数、`if`、`for`、`while`、状态回写和输出映射必须符合 `docs/C++代码规范.md` 第 3 章。
   - 调用子模块 `run()` 时，允许定义子模块输入、输出结构体变量。
   - 除子模块 `run()` 输入、输出结构体变量外，`run()` 函数体内禁止定义结构体变量或类对象。
   - 涉及物理、数学或控制含义的语句必须写函数体语句注释。

7. 规则 ID 级别闭环校验修复
   - 改写完成后必须执行本文档“规范符合性校验”章节。
   - 校验必须以 `docs/C++代码规范.md` 为唯一判定依据。
   - 校验结果必须写入 `<输出目录>/校验报告.md`。
   - 校验必须先完整检查全部生成代码，并生成问题清单。
   - 存在 `不通过` 项时，必须先汇总完整问题清单，再统一整改生成代码。
   - 整改完成后必须重新执行全量校验，不得只检查已整改文件或已知问题。
   - 检查、生成问题清单、整改、再检查构成一个闭环轮次。
   - 闭环最多执行 3 轮。
   - 超过 3 轮仍未完全修复时，必须停止改写，并在校验报告中说明剩余问题、对应规则 ID、证据、失败原因、已尝试整改动作和阻塞点。
   - 未满足“校验完成条件”时，改写不得视为完成。

## 规范符合性校验

组件代码改写完成后，必须以 `docs/C++代码规范.md` 为唯一判定依据，对生成代码进行规则 ID 级别的符合性校验。

校验目标不是概括说明“基本符合规范”，而是逐条证明生成代码是否满足 `docs/C++代码规范.md` 中的强制性规范。

### 校验基本原则

1. 校验必须覆盖 `docs/C++代码规范.md` 中所有适用于生成代码的规则 ID。
2. 每个校验项必须引用对应规则 ID。
3. 每个校验项必须给出证据。
4. 没有证据的检查项不得判定为 `通过`。
5. 明确违反规则时，必须判定为 `不通过`，不得用 `需确认` 替代。
6. 语义无法确认、原代码映射关系不足或需要用户判断时，判定为 `需确认`。
7. 存在任意 `不通过` 项时，本次改写不能视为完成。
8. 校验结果必须写入 `<输出目录>/校验报告.md`。

### 校验证据要求

每个校验项必须至少提供一种证据：

1. 文件路径。
2. 代码位置。
3. 扫描结果。
4. 构建命令结果。
5. 原始代码到生成代码的映射说明。
6. 人工比对说明。

证据必须能支撑判定结果。不能只写“已检查”“符合规范”“未发现问题”。

### 适用规则清单

校验前必须从 `docs/C++代码规范.md` 提取所有适用于生成代码的规则 ID，形成适用规则清单。

校验报告中的 `规则校验明细` 必须覆盖适用规则清单中的每个规则 ID。

规则 ID 不适用时，必须在适用规则清单中标记为 `不适用`，并写明不适用原因和证据，不得直接省略。

### 不适用规则判定

规则不适用只能用于生成代码确实不存在该结构的情况，例如无全局状态时 `GlobalContext.cpp` 相关规则不适用。

不适用必须给出代码证据或结构证据。

不得用 `不适用` 规避明确违规。

### 必须命令化校验项

以下校验必须提供命令输出或扫描结果：

1. 工程结构。
2. 文件命名。
3. `.cpp` include。
4. `.hpp` include。
5. 第三方依赖。
6. 外部框架 include 路径。
7. `FuncModule.hpp` 模板一致性。
8. `run()` 数量。
9. 自包含 CMake 配置和编译。

### 校验分层

校验分为三层。

#### 第一层：机械校验

机械校验用于检查可以通过文件扫描、文本检查或构建命令确认的规则。

必须检查：

1. 工程结构是否包含 `include/`、`src/`、`CMakeLists.txt`。
2. 是否生成 `include/FuncModule.hpp`。
3. `include/FuncModule.hpp` 是否与 `docs/C++代码规范.md` 中的固定模板一致。
4. 文件命名是否符合 `类名.hpp`、`类名.cpp` 或 `类名Types.hpp`。
5. `.cpp` 文件是否只包含自己的同名 `.hpp`。
6. `.hpp` 文件是否只包含自定义 `.hpp` 和 C++ 标准库头文件。
7. 是否存在相对路径或绝对路径 include。
8. 是否存在第三方开源库头文件或第三方 API 使用。
9. `CMakeLists.txt` 是否引用外部框架 include 路径。
10. 生成代码是否可以自包含配置和编译通过。

#### 第二层：结构校验

结构校验用于检查组件代码是否满足规范化结构。

必须检查：

1. 每个模块是否有独立模块类。
2. 每个模块类是否继承 `FuncModule<类名Traits>`。
3. 每个模块是否有 `{ClassName}Traits`。
4. Traits 是否包含 `Input`、`Output`、`Param`、`State`、`Sub`。
5. 接口字段类型是否符合规范。
6. 构造函数是否符合固定写法。
7. `Sub{...}` 内所有子模块构造表达式是否符合 `CTOR-013`、`CTOR-028`、`CTOR-029`、`CTOR-030`、`CTOR-031`、`CTOR-032`、`CTOR-033`、`CTOR-034`、`CTOR-035` 和 `CTOR-036`，每个子模块构造的第一个实参是否为对应的 `子模块Traits::Param{...}` 临时对象，第二个实参是否为对应的 `子模块Traits::State{...}` 临时对象。
8. 子模块实例是否声明在父模块 `Traits::Sub` 中，并在父模块构造函数初始化列表的 `Sub{...}` 内构造；`Sub{...}` 是否只初始化父模块持有的子模块实例，`std::move(param)` 和 `std::move(state)` 是否只初始化当前父模块自身的 `param_` 和 `state_`。
9. 非空子模块 `Param{...}` 和 `State{...}` 临时对象内部是否使用 `.field = value` 字段初始化方式绑定参数或状态字段；嵌套结构是否也使用 `.field = value` 字段初始化方式表达字段来源。
10. 子模块 `Param{...}` 和 `State{...}` 临时对象内部是否递归展开到最底层基础字段；多层嵌套结构是否逐层继续使用 `.field = value` 指定初始化，直到叶子字段为标量、枚举、标准库值类型或规范允许的基础类型表达式。
11. 是否存在把完整结构体对象、父模块聚合字段、子模块参数对象、子模块状态对象或局部结构体变量整体赋给某个字段的写法，例如 `.childParam = param.childParam`、`.state = state.childState`、`.pidParam = pidParam0`。
12. 是否存在直接传入裸 `param.xxx`、裸 `state.xxx`、局部变量、非对应 Traits 临时对象、非 Traits 包裹实参，或 `ChildModuleTraits::Param{param.childParam}`、`ChildModuleTraits::State{state.childState}` 这种位置聚合初始化写法。
13. 是否错误生成或要求父模块 `Param`/`State` 中存在 `childParam`、`childState` 等字段作为子模块参数或状态固定存储位置。
14. 每个 `.cpp` 是否仅实现一个模块的 `run()`。
15. `run()` 签名是否固定为 `void 类名::run(const Input& input, Output& output)`。
16. 所有可扫描代码是否位于命名空间中。
17. 注释是否符合规范要求，是否满足 `CMT-037` 的中文注释和中文业务术语保留要求。

子模块构造校验证据必须包含文件路径、`Traits::Sub` 字段位置、构造表达式位置、违规实参序号、违规实参文本、字段初始化检查结果、最大嵌套层级、叶子字段清单、是否递归展开到最底层基础字段的检查结果，以及父模块 `Param`/`State` 是否被错误用于存放子模块参数或状态的检查结果；发现违规时，必须引用 `CTOR-013`、`CTOR-028`、`CTOR-029`、`CTOR-030`、`CTOR-031`、`CTOR-032`、`CTOR-033`、`CTOR-034`、`CTOR-035` 或 `CTOR-036` 判定为 `不通过`。

#### 第三层：函数体和语义校验

函数体和语义校验用于检查 `run()` 实现是否严格遵循规范，并保持原始算法语义。

必须检查：

1. `run()` 函数体内是否禁止使用指针。
2. `run()` 函数体内是否禁止定义非子模块输入输出结构体变量或类对象。
3. 四则运算结果是否先赋值给具名局部变量。
4. 标准库函数调用结果是否先赋值给具名局部变量。
5. 所有 `std::min`、`std::max`、`std::clamp`、`std::sqrt`、`std::abs`、`std::fabs` 等标准库函数调用的实参是否禁止包含 `+`、`-`、`*`、`/` 四则运算表达式。
6. 是否存在只检查标准库函数调用结果赋值、但漏检标准库函数实参中嵌入四则运算表达式的情况。
7. `if/else` 是否满足分支合流变量写法。
8. `for`、`while` 是否满足循环携带变量写法。
9. 状态回写是否显式。
10. 输出映射是否显式。
11. 涉及物理、数学或控制含义的语句是否有注释。
12. 原始代码中的输入、输出、参数、状态和核心算法语句是否能映射到生成代码。

标准库函数实参校验证据必须包含文件路径、代码位置、函数调用文本和嵌入的四则表达式；发现违规时，必须引用 `BODY-098` 或 `BODY-099` 判定为 `不通过`。

### 闭环校验修复

校验不通过时，必须进入闭环校验修复流程。闭环流程由“检查、生成问题清单、整改、再检查”组成。

1. 每轮必须全量校验 `<输出目录>/` 下全部生成代码、`CMakeLists.txt`、`include/FuncModule.hpp` 和 `校验报告.md`。
2. 每轮必须覆盖所有适用于生成代码的规则 ID。
3. 每轮必须生成完整问题清单。
4. 问题清单必须包含规则 ID、问题类型、文件路径、证据、违反原因和建议修复方式。
5. 存在 `不通过` 项时，必须先汇总完整问题清单，再统一整改生成代码。
6. 整改必须针对全部生成代码进行，不得只局部修复单个已发现问题。
7. 整改完成后必须重新执行全量校验，不得只检查已整改文件或已知问题。
8. 每轮校验和整改结果必须写入 `<输出目录>/校验报告.md` 的“闭环校验修复记录”和“问题清单”。
9. 闭环最多执行 3 轮。
10. 超过 3 轮仍存在 `不通过` 项时，必须停止改写。
11. 出现语义无法确认、原始代码信息不足、第三方依赖无法隔离，或继续整改会改变原算法语义时，必须停止或标为 `需确认`。
12. 停止时必须说明剩余问题、对应规则 ID、证据、失败原因、已尝试整改动作、阻塞点和需要用户确认的信息。

### 判定标准

校验时必须按以下标准判定：

1. 有明确代码证据且符合规则，判定为 `通过`。
2. 有明确代码证据且违反规则，判定为 `不通过`。
3. 规则依赖业务语义、原始意图或用户决策，且当前证据不足，判定为 `需确认`。
4. 编译失败时，构建相关规则必须判定为 `不通过`。
5. 发现第三方依赖使用时，第三方依赖规则必须判定为 `不通过`。
6. 发现 `.cpp` 包含非自身 `.hpp` 时，include 规则必须判定为 `不通过`。
7. 发现 `run()` 外还有其他函数实现时，`run()` 数量规则必须判定为 `不通过`。

### 校验完成条件

只有同时满足以下条件，改写才可以视为完成：

1. 已生成适用规则清单。
2. 所有适用规则 ID 均已出现在校验报告中。
3. 所有不适用规则均给出不适用原因和证据。
4. 所有机械校验项均有证据。
5. 所有必须命令化校验项均有命令输出或扫描结果。
6. 所有结构校验项均有证据。
7. 语义校验已给出原始代码到生成代码的映射。
8. 不存在 `不通过` 项。
9. 自包含构建通过。

## 改写边界

- 改写必须保持原算法语义，不得重写算法为不同数学模型。
- 不得凭空新增业务输入、输出、参数或状态。
- 不明确的业务含义必须标为 `需确认`，不得自行命名为固定物理量。
- 外部依赖无法改写为可扫描组件代码时，必须隔离到组件边界外，并在校验报告中说明。
- 改写输出目录是生成产物目录，不作为规范源文件维护。

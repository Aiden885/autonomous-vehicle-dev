# APA 与 CARLA 联调代码评估

日期：2026-11-13。对象：`apa_1112.zip` 与 `carla_bridge_1112.zip`。

## 1. 先说结论

这两个包已经不是简单地给 Simulink 生成代码套一个 C++ 外壳，而是在继续开发一套可交互的 APA 仿真运行系统：有任务管理、搜索规划、路径验收、跟踪控制、踏板执行、在线安全和测试页面。

总体上，工程设计有不少值得保留的地方，但当前版本还不适合直接当成稳定交付版本。我实际复现了两个需要先处理的问题：**合法直线路径会因离散点与里程不一致被拒绝；默认启动脚本会把车型配置的相对路径解析错。** 此外，随包测试没有全部通过，部分测试明显落后于实现。

至于“泊车效果好不好”，目前证据不足，不能从源码齐全、能编译或者有规划成功标志直接下结论。本轮没有启动 CARLA 物理闭环，也没有完成 Pangu 全链路构建。

原压缩包、解压后的算法及桥接源文件均未修改。本轮仅做解包、离线构建、测试、调试和记录。

## 2. 先需要解决的问题

### 2.1 高优先级：直线路径的点间距离与里程增量不一致

**这是在生产离散化函数中复现的问题，不只是测试预期写错。**

原包的 `parking_search_direction_regression` 使用确定性搜索替身提供直线路径，再走实际的路径适配、离散化和安全门。第一个用例就在安全门前失败。

调试得到的路径开头是：

```text
X 坐标：       0.00,  0.24,  0.36,  0.48,  0.60 ... m
对应 Odo：    -0.12, -0.12, -0.12, -0.12, -0.12 ... m
```

该用例车头朝向约 π，车辆倒车，所以 X 正向增加而 Odo 为负并不矛盾。真正的问题是：**第一段实际跨了 0.24 m，却只登记了 0.12 m 的行驶里程。**

原因位于 [geoLnDirectDisctet.c:186](/data/aiden/文档/Pro/APA/联调代码审阅_20261113/apa_1112/apa/apa/module_lib/apa_algorithm/apa/geoLnDirectDisctet.c:186)：

- 第一个采样点在车辆附近，触发 `condReset`，只把点数设回 1，没有把该点写入输出。
- 但后面仍把内部采样位置推进到了这个被跳过的点。
- 下一轮存入第二个输出点时，坐标已经跨了两个步长，Odo 却仍按一个步长写入。

因此 [apaPathInterval.h:11](/data/aiden/文档/Pro/APA/联调代码审阅_20261113/apa_1112/apa/apa/module_lib/apa_algorithm/apa/apaPathInterval.h:11) 的区间一致性检查拒绝它，最终回归在 `assert(accepted)` 终止。

**可能表现**：规划已经给出几何上可用的候选，但转换为执行路径后被拒绝；可能减少可接受候选、增加求解时间，或最终报告规划失败。不能由此推断所有车位都失败，也不能直接推断会撞车。

**建议处理方向**：明确“贴近车辆时清理路径”的语义，确保清理后的起点仍是实际车辆位姿，且每段坐标、航向和有符号 Odo 对得上；补充直线首段、圆弧首段和换向点用例。不要靠放宽安全门容差绕过这个问题。

### 2.2 高优先级：默认 run.sh 启动时车型文件路径失效

[run.sh:75](/data/aiden/文档/Pro/APA/联调代码审阅_20261113/carla_bridge_1112/carla_1016/carla/scenarios/apa/run.sh:75) 读取原配置，修改地图、车位和 CARLA 路径后，把配置写入默认位置：

```text
/tmp/apa-pangu-carla/carla/bridge_config.runtime.json
```

但 [bridge_config.json:38](/data/aiden/文档/Pro/APA/联调代码审阅_20261113/carla_bridge_1112/carla_1016/carla/scenarios/apa/bridge_config.json:38) 中的车型文件仍是相对路径：

```text
../../../../pangu_gaasd_base/modules/apa/apa/conf/apa_vehicle_profile.json
```

Bridge 在 [carla_bridge_apa.py:4221](/data/aiden/文档/Pro/APA/联调代码审阅_20261113/carla_bridge_1112/carla_1016/carla/tools/carla_bridge/carla_bridge_apa.py:4221) 按配置文件所在目录解析它。配置移到 `/tmp` 后，实际解析成：

```text
/pangu_gaasd_base/modules/apa/apa/conf/apa_vehicle_profile.json
```

本机实测该路径不存在，加载直接抛出 `FileNotFoundError`。即便两个项目已经按预期兄弟目录关系摆好，默认脚本仍会遇到这个问题。直接使用原目录配置或另行指定配置位置，不一定触发它。

**建议处理方向**：在生成运行配置前，按原配置目录把车型文件等相对资源路径转换为绝对路径，再写入临时配置。不要要求使用者在根目录创建一个假目录来适配。

### 2.3 中优先级：测试与实现未同步，不能把随包回归作为可靠放行依据

补齐目录关系后，APA Python 测试共运行 75 项：57 项通过，4 项断言失败，14 项异常。Python 3.8 与 3.12 的结果一致，不是只在某一个 Python 版本上出现。

已经核实的不同原因包括：

- 测试用 `object.__new__` 绕过正常构造，未同步补充 `session_id`、`pending_map_config`、`_planning_query_region` 等字段，运行时出现属性缺失异常。真实构造及场景加载流程有相应初始化，不能据此宣称生产对象也缺这些字段。
- 有的测试仍假设直接用“等效前轮转角 / 最大转角”换算 CARLA steer，而当前实现已引入等效单轨转角到内侧车轮转角的几何换算。
- 车轮限角用例仍拿旧的控制限角作为物理车轮限角预期，与当前共享车型中二者分开的做法不一致。
- 一个终点净空用例的目标位置预期与实现不符；本轮未把它认定为已证实的碰撞缺陷，还需核对几何约定及预期值。

示例见 [测试构造器:57](/data/aiden/文档/Pro/APA/联调代码审阅_20261113/carla_bridge_1112/carla_1016/carla/tools/carla_bridge/tests/test_apa_bridge_contract.py:57) 和 [车轮限角用例:1265](/data/aiden/文档/Pro/APA/联调代码审阅_20261113/carla_bridge_1112/carla_1016/carla/tools/carla_bridge/tests/test_apa_bridge_contract.py:1265)。

应该先更新测试夹具和接口预期，再逐项判断剩余失败；不能直接删掉失败测试，也不能将 18 项不通过全部算成 18 个实际驾驶缺陷。

## 3. 两个包现在怎样配合

可以把主要链路理解为：

```text
CARLA 车辆状态、地图和障碍物
    -> Python Bridge：后轴坐标、车位/目标、场景、任务和帧编号
    -> ZMQ 输入节点：JSON 校验和 Protobuf 组装
    -> ApaModule：任务状态、规划调度、路径跟踪和在线安全
    -> 独立规划 worker：候选搜索、离散化、安全与可执行性检查
    -> C 控制与执行器：转角、速度/加速度及最终踏板
    -> ZMQ 输出节点
    -> Python Bridge：核验身份、当前帧、车型和执行指令
    -> CARLA VehicleControl
```

### 3.1 规划不只是调用一个生成函数

四类车位泊入和泊出经过业务分支选择，使用几何连接、结构化搜索及 Reeds–Shepp 连接等手段产生候选。候选还要经过路径结构检查、碰撞/边界检查，以及名义执行预演。

泊入搜索允许从目标区域锚点向实际车辆搜索，再把结果转换为车辆实际执行方向；泊出则需要固定实际车辆为起点。这种区别是有物理意义的，不能简单把泊入路径的数组反过来就认为支持泊出。

搜索运行在独立进程中，能取消或终止；主进程继续管理任务和停车。这比把耗时搜索直接塞在控制周期中更合理。

### 3.2 控制和踏板的归属与此前 ACC 调试方式不同

当前 APA 的 `apaMocoParkingControl` 包含控制状态、参考点处理、纵向控制和横向控制。纵向代码已有速度误差 PI、加速度反馈、积分及加速度/jerk 限制；还处理换向、段末接近和停车状态。

最终油门、制动和挡位由 C 函数 `apaMocoActuate` 生成；运行封装把执行器所有者标成 `C:apaMocoActuate:v2`。Bridge 验证后执行这些踏板，**不是再在 Bridge 中叠一个速度 PID 来重新算油门**。

执行器里考虑了反馈滤波、加速度偏置积分、坡度项、油门变化率、起步保持和超速停车。说明作者在处理低速车辆动力学，而不是只做路径几何演示。不过这些参数与名义模型是否适配实际 CARLA 车型，仍要看物理闭环记录。

### 3.3 当前环境信息主要是仿真真值与离线底图

Bridge 使用 CARLA actor、离线地图、车位文件等构造算法场景。这可以验证规划控制，但不等于已经验证了原 Simulink 中完整的传感器感知、车位识别与融合链路。

因此这两个包不能直接视为“原 Simulink 所有功能均已复现”，也不能视为已经完成的 GAASD 画布工程。`XXX` 目录中的 FuncModule 封装是已有基础，完整任务管理、控制调度及部分安全逻辑仍在运行封装/C 入口中。后续上画布时还需明确哪些作为组件、哪些留在运行框架。

## 4. 代码中值得保留的设计

- **接口检查比较认真**：检查必需字段、有限值、数组容量、会话/任务/帧与仿真时钟，避免无效数据被默默补零后继续控制。
- **车型来源统一**：同一份 JSON 生成 C 端车型常量，Bridge 和算法用摘要确认一致，减少轴距、车体包络及转角尺度不一致的问题。
- **周期同步考虑较完整**：相同帧重发不应重复推进控制状态，反馈和响应按帧对应，再推进物理仿真。
- **安全停车不完全依赖算法正常返回**：桥接侧有独立制动、停稳确认、碰撞锁存和指令确认；多项相关模拟对象测试本轮通过。
- **规划与执行检查能够复用**：候选预演与在线跟踪共用控制入口，比规划端只看路径不看实际控制可执行性更扎实。
- **文档有边界意识**：明确说明预算耗尽不等于几何无解、名义预演不代表真实物理响应、规划成功不等于泊车完成。这些边界应该保留。

需要注意，共享代码也意味着共同盲点：预演与在线都调用同一段控制代码，并不能相互证明这段代码正确；仍需独立物理测试。

## 5. 本轮实际做了哪些验证

### 5.1 C/C++ 离线构建与回归

在包外新建构建目录，使用 Clang 10、C99/C++20，按包内测试工程编译，算法库及 FuncModule 库构建成功。测试工程配置了 `-Wall -Wextra -Werror`。

四项 CTest 结果：

- `tracking_regression`：通过。
- `actuator_regression`：通过。
- `slot_guidance_regression`：通过。
- `parking_search_direction_regression`：失败，原因见 2.1。

另建 Debug 构建，通过 GDB 核实跳点位置与输出数组，不是只根据报错文字猜测。

这些回归不包含完整 Pangu 业务节点构建。可选 `input_contract_regression` 默认关闭，依赖 Pangu 生成的 Protobuf 和 SDK，本轮未构建执行。方向回归使用搜索替身，不能代表真实图搜索的成功率和耗时。

### 5.2 Bridge 与页面离线测试

两个源码包需要按预期项目关系组合。最初单独解包运行会找不到共享车型文件；本轮只在审阅目录建立测试用软链接，把包内 APA 模块映射到 `pangu_gaasd_base/modules/apa/apa`，没有修改源码。

补齐后：

- APA Bridge 相关测试：75 项，57 项通过、4 项失败、14 项异常；Python 3.8/3.12 结果一致。
- 页面 APA 运行健康检查：3 项，全部通过。这里只验证健康检查逻辑，不代表真实服务已启动。
- 额外执行页面全量历史测试：50 项，7 项失败、15 项异常；多项依赖包中未沿用的 ACC/LKS 场景编号或旧页面行为，不计作 APA 泊车缺陷，但说明整个包的历史测试也未保持全绿。

### 5.3 包和交付检查

APA 包有 338 个文件；Bridge 包有 1,421 个文件，混入 Git 历史对象、缓存、历史诊断及 CARLA PythonAPI 二进制包，不是一个精简的 APA 可部署发布包。

Bridge 归档含 CARLA 0.9.15 的 cp27/cp37 API 包，而共享车型标注 CARLA 0.9.16；启动脚本优先使用外部 `CARLA_ROOT` 和 Python 3.8。这里不能据此认定所有启动都会版本冲突，但交付时必须明确实际服务器与 PythonAPI 的版本来源，不能让对方随便从包里挑一个 API 安装。

解压审阅时未展开 Git 历史、Python 字节码和 wheel/egg；全部 `.pt` 文本配置已保留。核对所有保留的原文件与 ZIP 内容，APA 338 个、Bridge 481 个文件均一致。

## 6. 现有记录能否说明泊车效果

包内找到两份 APA 诊断快照，但不是同一次任务的完整开始到结束记录：

- `task-start.json`：Town04，任务 11；记录的是任务开始，该快照记录的 7 个桥接源码摘要与本包一致，但没有完成过程和结束结果。
- `last-event.json`：Town15，任务 3；阶段为任务准入，原因是“起点距离目标过远，车位超出本次规划查询范围”。其中 Bridge 主文件和离线地图文件摘要与本包不一致，不能拿它作为当前代码的故障复现结果。

两份文件的会话也不同。不能把它们拼起来当作一次测试。诊断器按端点维护有界快照并覆盖文件，本来就不是完整的批量测试历史。

本轮没有得到当前版本连续的位姿、速度、路径误差、实际踏板、碰撞和最终停稳记录，因此暂时回答不了：几类车位成功率多少、终点误差多大、换向是否平顺、是否经常恢复、一次停车耗时多少。

包内 `docs/TESTING.md` 也明确提到 Town15/108 等修正需要新闭环，不能沿用旧结果。合理结论是：**设计上已有闭环能力，当前物理效果还没有被这次材料和本轮测试充分证明。**

## 7. 下一步建议

1. 先修复直线离散化的一致性问题和默认启动配置路径问题，保持安全门不放松。
2. 同步桥接测试夹具、车型/转向换算预期；先获得可信的离线回归基线。
3. 将完整 Pangu 编译安装物、worker、节点配置和共享车型固定为一套版本，确认加载的不是旧动态库。
4. 从一个宽松垂直车位开始，依次验证泊入、泊出、连续任务和中途取消，再扩展其他车位及障碍场景；不要一开始同时调地图、控制和搜索。
5. 每次保存完整任务记录，区分“规划成功”“开始执行”“恢复或失败”“实际到位并停稳”。至少包含终点位置/航向误差、速度、碰撞、换向及恢复次数和总耗时。
6. `attempt_timeout_sec` 当前为 0，关闭了 worker 墙钟看门狗；搜索虽有展开等预算，仍不等于有明确总响应时限。后续测试单独记录耗时，再决定是否启用时间预算，不能把 `recovery_timeout_sec=15` 误认为整个规划一定 15 秒结束。

总结：目前适合继续作为 APA 研究和 GAASD 组件化的基础，不宜直接把它称为已经验证稳定的完整泊车系统。先把可重复的错误和测试基线处理好，再看 CARLA 效果，判断才可靠。
